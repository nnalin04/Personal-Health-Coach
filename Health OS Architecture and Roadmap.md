# **Architectural Specification for the Health OS: A Multi-Modal, Scalable, and Empathetically Driven Mobile Ecosystem**

The development of a modern Health OS necessitates a departure from traditional, transactional health-tracking applications. The core architectural philosophy is "invisible tracking," a paradigm where the user interface serves as a narrow portal to an expansive, intelligent backend capable of distilling unstructured human activity—captured via natural language, photography, and clinical documentation—into actionable, longitudinal health insights.1 This specification outlines a high-performance, fault-tolerant infrastructure designed to serve as the foundational blueprint for a comprehensive health ecosystem. By integrating a Spring Boot orchestration layer with a Python-based intelligence engine and an offline-first mobile architecture, the system ensures that tracking remains low-friction and highly adaptive to the user's regional and cultural nuances.4

## **UI/UX Architecture and Offline-First Mobile Strategy**

The mobile application is designed as a minimalist, three-page environment, prioritizing conversational interaction over complex navigational hierarchies. This structure aims to lower the psychological barrier to health logging, particularly for users managing chronic conditions or dietary goals who often find manual data entry prohibitive.2

## **The Minimalist Three-Page Architecture**

The interface is strictly bounded to three functional views, each optimized for a specific stage of the user’s daily health journey.

| Page | Functionality | Technical Role |
| :---- | :---- | :---- |
| **Page 1: Onboarding/Auth** | Conversational onboarding via a chat-based data collection engine. | Captures the user's Taste\_Profile and Health\_Baseline through an empathetic dialogue.1 |
| **Page 2: The Dashboard** | Read-only, unified view featuring an "Action Ring" and contextual AI suggestions. | Pulls synchronized data from the local WatermelonDB to present real-time progress without re-fetching.9 |
| **Page 3: Omni-Chat Interface** | The primary input engine with a universal '+' button for multi-modal uploads. | Serves as the gateway for text, food images, and medical PDFs into the backend event stream.11 |

## **Mobile Caching and State Management**

To maintain a responsive interface across diverse network conditions, the application implements an offline-first database strategy using WatermelonDB.9 This choice is motivated by the need for a high-performance, observable local database that can handle complex queries and large datasets (such as a multi-year history of meal logs) on the device.10

WatermelonDB operates as a reactive layer over SQLite, allowing the UI to remain in sync with the underlying data state automatically. The synchronization protocol between the React Native client and the Spring Boot backend follows a strict two-phase logic to ensure eventual consistency and robust conflict resolution.9

#### **The Synchronization Lifecycle**

1. **Pull Phase:** The mobile client initiates a request to the backend with a lastPulledAt timestamp.14 If this is the initial sync, the timestamp is null, triggering a full fetch of all accessible records. The server responds with a consistent view of changes (created, updated, and deleted records) occurring after that timestamp.14  
2. **Push Phase:** The client identifies all locally modified records since the last sync. These changes are pushed to the backend, which applies them to the master PostgreSQL database.13  
3. **Conflict Resolution:** The system utilizes a per-column client-wins strategy. If a conflict is detected—where a record has changed on both the server and the client—the server's version is generally accepted except for the specific columns modified locally.13  
4. **Consistency Enforcement:** The backend must provide a consistent view by performing queries under a write lock or by returning a timestamp marked before the query process begins to ensure no changes are missed during the fetch.14

This architecture permits the user to continue interacting with the Omni-Chat and viewing their Dashboard even while offline. Local IDs generated by the mobile app are treated as true IDs by the backend, leveraging the high entropy of standard Watermelon IDs to prevent collisions.15

## **Monorepo Architecture and Folder Organization**

The project is organized into a standardized monorepo to facilitate synchronized development between the mobile frontend, the orchestration backend, and the AI services. This structure is essential for an AI coding assistant (Claude Code) to bootstrap the project, as it defines clear boundaries while sharing necessary API contracts and data schemas.

## **High-Level Folder Structure Directive**

The monorepo hierarchy is designed to isolate environments while maintaining a shared "source of truth" for system-wide definitions.

| Directory Path | Description | Responsibility |

## **Backend Microservices and Distributed Infrastructure**

The backend is built as an event-driven system, utilizing Spring Boot as the reliable "Orchestrator" and FastAPI as the "AI Engine." This separation of concerns allows for the heavy computational loads associated with computer vision and LLM orchestration to scale independently of the relational data and authentication layers.3

## **The Orchestrator (Spring Boot)**

The Orchestrator serves as the entry point for all mobile traffic. Its primary functions include:

* **JWT Authentication and Identity Management:** Handling user sign-up, login, and secure token issuance.  
* **API Gateway:** Routing requests and providing the synchronization endpoints for WatermelonDB.9  
* **Relational Persistence:** Managing the primary PostgreSQL database for user profiles, basic habit logs, and audit trails.18  
* **WebSocket Orchestration:** Pushing real-time notifications to the mobile app when long-running AI tasks (like processing a multi-page medical PDF) are complete.28

## **The AI Engine (Python / FastAPI)**

The FastAPI service is the intelligence hub of the Health OS. It is designed to interface with the latest multi-modal foundation models and vector stores.

* **Vision Pipelines:** Utilizing Gemini Vision for macronutrient estimation and food identification.23  
* **Document Intelligence:** Integrating Google Cloud Document AI to extract structured entities from medical reports.21  
* **RAG Correlation:** Using LangChain and pgvector to generate personalized, empathetic insights by correlating daily habits with clinical markers.20

## **Event-Driven Data Flows and the Message Broker**

Asynchronous handoffs are critical for maintaining a "low-friction" experience. When a user uploads a large file, the Orchestrator does not process it synchronously. Instead, it publishes an event to RabbitMQ, which the AI Engine consumes.19

| Task Type | Broker Strategy | Payload Pattern |
| :---- | :---- | :---- |
| **Food Recognition** | Direct Queue | Metadata \+ S3 URL for immediate vision processing.12 |
| **Large PDF OCR** | Claim Check Pattern | Message contains a reference to the PDF stored in external storage (S3).25 |
| **RAG Insight Gen** | Redis Stream | High-throughput streaming for real-time dashboard suggestions. |

## **Data Persistence and Privacy Engineering**

The database architecture leverages PostgreSQL with the pgvector extension to handle both relational health data and high-dimensional embeddings. Given the sensitive nature of medical data in India, the system must comply with the Digital Personal Data Protection (DPDP) Act of 2023, requiring rigorous encryption and consent management.33

## **The PostgreSQL \+ pgvector Schema**

The schema is divided into three logical domains: identity, time-series logs, and medical knowledge.

#### **Database Schema Definition**

| Entity | Primary Attributes | Relationship / Constraint |
| :---- | :---- | :---- |
| Users | id (UUID), email\_encrypted (BYTEA), pass\_hash | Master entity for all data.18 |
| Taste\_Profiles | user\_id (FK), regional\_pref, staple\_grains, restrictions | Captures cultural food nuances.5 |
| Blood\_Metrics | id, user\_id, marker\_name, value, unit, test\_date | Structured clinical data from OCR.31 |
| Meal\_Logs | id, user\_id, dish\_name, calories, macros (JSONB), image\_url | Time-series habits for correlation.1 |
| Knowledge\_Base | id, content (TEXT), embedding (VECTOR(1536)) | RAG vector store for health advice.20 |

#### **Data Privacy and Field-Level Encryption**

To satisfy the DPDP Act's "reasonable security safeguards," all sensitive medical fields must be encrypted at rest using AES-256.34 In the Spring Boot environment, this is implemented at the JPA level using @ColumnTransformer or a custom AttributeConverter that utilizes the PostgreSQL pgcrypto extension.18

The encryption strategy ensures that:

* Fields like HbA1c levels or specific disease diagnoses are stored as bytea blobs.18  
* Encryption keys are managed outside the database layer, preferably in a secure Hardware Security Module (HSM) or a managed Key Management Service (KMS).  
* Search on encrypted fields is restricted to exact matches or handled via an auxiliary "blind index" to maintain high security while supporting necessary queries.27

Furthermore, the DPDP Act mandates a 72-hour breach notification window and strict consent management.35 The Users table includes a consent\_version and withdrawal\_requested flag to ensure that data processing stops immediately upon user revocation of rights.33

## **Vector Indexing for RAG Correlation**

For the RAG (Retrieval-Augmented Generation) engine, pgvector supports two primary indexing types: IVFFlat and HNSW.

* **HNSW (Hierarchical Navigable Small World):** Recommended for this architecture due to its superior recall and low latency in similarity searches, which is vital for providing real-time, personalized suggestions on the Dashboard.24  
* **Distance Metric:** The system utilizes Cosine Distance (vector\_cosine\_ops) or L2 distance (\<-\>) to identify the most relevant medical knowledge chunks relative to the user's current health metrics.20

## **AI Workflows and Routing Strategy**

The intelligence layer must distinguish between tasks requiring "Light AI" (simple text chat) and "Heavy AI" (multi-modal vision and complex document parsing). This is managed by the "Smart Router" within the FastAPI service.11

## **The Smart Router Logic**

Incoming Omni-Chat inputs are first processed by a lightweight classification model.

1. **Classification:** The router determines if the input is a \[Food Image\], \`\`, or \[General Health Query\].  
2. **Path Selection:**  
   * **Food Path:** Routed to the Gemini Vision pipeline.23  
   * **Medical Path:** Routed to the Google Cloud Document AI and Healthcare NLP services.21  
   * **Query Path:** Routed to the RAG Correlation Engine for context-aware responses.20

## **Food Logging: Vision with Graceful Fallback**

The food logging pipeline is optimized for the vast diversity of Indian cuisine. Standard vision models often fail to distinguish between visually similar regional dishes (e.g., various types of *dal* or *bhakri*).2

#### **Regional Adaptation Pipeline**

| Step | Technique | Goal |
| :---- | :---- | :---- |
| **1\. Vision Analysis** | Gemini 1.5 Flash Vision API | Identify the primary dish and estimate portion sizes using reference objects.1 |
| **2\. Contextual Filtering** | User Taste\_Profile Cross-Ref | Prioritize regional variants (e.g., if user is from Rajasthan, "Bajra" is the default grain assumption).5 |
| **3\. Graceful Fallback** | Proactive Dialogue | If confidence is \<0.80, the AI generates a prompt: "I see a yellow dal. Is this Toor Dal or Moong Dal?".23 |
| **4\. Macro Estimation** | Indian Food Database API | Calculate calories, proteins, and fats based on the confirmed dish and estimated portion.1 |

## **Medical OCR and Clinical Data Extraction**

For medical reports, the AI Engine utilizes Google Cloud Document AI's OCR processor, which preserves the structural layout (paragraphs, tables, and blocks) of lab results.21

1. **Extraction:** The OCR engine identifies table cells and headings in blood test results.21  
2. **Clinical Entity Mapping:** The Healthcare NLP API maps the extracted text to medical terminologies like LOINC (for lab tests) or SNOMED CT (for conditions).31  
3. **Structured Transformation:** Results are converted into a standardized format (inspired by HL7 FHIR) and stored in the Blood\_Metrics table.31

## **The RAG Correlation Engine**

The final piece of the intelligence layer is the RAG correlation engine. Using LangChain, the Python service performs a vector search over the medical knowledge base and the user's historical Meal\_Logs. It then generates a personalized notification for the Dashboard Page 2\.

* **Mechanism:** "The user’s Vitamin D is low and their recent logs show low intake of fortified cereals or dairy \[from Food Vision\]. Generate an empathetic suggestion to spend 15 minutes in the sun or increase specific regional foods".6  
* **Prompt Orchestration:** The response must be non-judgmental and supportive, avoiding clinical jargon while maintaining medical accuracy.

## **Step-by-Step Implementation Roadmap**

The development is structured into five logical phases to ensure architectural integrity and data safety.

## **Phase 1: Infrastructure and Secure Persistence**

1. Initialize the monorepo and Docker environments for PostgreSQL, RabbitMQ, and Redis.16  
2. Deploy the Orchestrator with Spring Security (JWT) and pgcrypto field-level encryption.17  
3. Implement the baseline schema for Users and Taste\_Profiles.

## **Phase 2: Mobile Foundation and Sync Protocol**

1. Bootstrap the React Native app with WatermelonDB and the 3-page minimalist UI.10  
2. Develop the pullChanges and pushChanges endpoints in the Orchestrator to enable offline-first capabilities.9  
3. Test sync performance with simulated high-latency networks to ensure UI responsiveness.

## **Phase 3: AI Intelligence and Smart Routing**

1. Deploy the FastAPI AI Engine and connect it to RabbitMQ.19  
2. Implement the Smart Router to classify incoming Omni-Chat media.11  
3. Build the Food Vision pipeline with Gemini Vision, integrating regional Indian diet logic and the "Graceful Fallback" conversation states.1

## **Phase 4: Clinical OCR and RAG Integration**

1. Integrate Google Cloud Document AI for medical report parsing.21  
2. Set up the pgvector knowledge base and implement the LangChain correlation engine for the Dashboard suggestions.20  
3. Establish the WebSocket bridge between the Orchestrator and the Mobile App to notify users when clinical processing is complete.28

## **Phase 5: Regional Refinement and Compliance**

1. Fine-tune the vision models for regional variations, including quick-commerce receipt parsing (Blinkit/Instamart).12  
2. Perform a full security audit against the DPDP Act requirements, ensuring consent withdrawal mechanisms and encryption keys are properly managed.34  
3. Launch the "Invisible Tracking" pilot to gather feedback on the empathetic tone of the AI suggestions.

## **Conclusion and Future Outlook**

The Health OS architecture presented here addresses the critical challenges of user friction and clinical data fragmentation. By leveraging an offline-first mobile strategy, the system remains reliable in low-connectivity environments, while the event-driven backend allows for sophisticated, high-latency AI processing to occur without blocking the user experience.10 The integration of cultural and regional dietary knowledge transforms a generic calorie tracker into a "Health OS" that understands the user’s specific context.36 This blueprint provides the rigorous technical structure necessary for Claude Code to execute a production-grade build, ensuring that scalability, privacy, and empathy are encoded into the very first lines of the project.
